## 2. Regression Analysis

### No Breaking Changes Detected

1. **Dashboard compatibility:** The N2 privacy payload reduction is backward-compatible. The dashboard's `PrivacyTab.tsx` (L20-22) uses `privacy.privacy?.accessRoles || {}` — the optional chaining handles the missing field for non-owner responses. Since the dashboard user is always the collection owner (authenticated via SIWE cookies with `credentials: 'include'`), they receive the full payload.

2. **N3 whitelist auth:** The dashboard does not directly call `/api/v1/whitelist`. Whitelist management is a server-side/CLI operation. No UI impact.

3. **N1 roles auth:** The dashboard's `PrivacyTab.tsx` uses `apiPost` for role grant/revoke (which includes cookies), not `apiGet` for the roles list. The GET roles endpoint is only used in integration tests (now updated with auth headers).

4. **N4 error handling:** The `grantAccess()` and `revokeAccess()` calls now happen after the explicit ownership check, so the delegated ownership validation in `PrivacyManager` serves as a redundant safety net (defense in depth). The renamed `updatedPrivacy` variable avoids the `const privacy` shadowing that was present in the original code.

5. **N6 balance format:** The `balance` field now returns a string like `"1.234567"` instead of `"1.234567"` from `toFixed(6)`. Format is identical. The `balanceWei` field (string) is unchanged.

## 3. New Observations

### O1. `req.params.name` echoed in N4 error message — Info

```typescript
return reply.status(404).send({ ok: 0, errmsg: `Collection "${req.params.name}" has no privacy settings...` });
```

`req.params.name` is user-controlled input reflected in the response body. This is a JSON API (not HTML), so no XSS risk. However, it could leak information about what collections exist vs. don't exist (404 vs. 200). Since the endpoint already requires authentication, this is acceptable.

**Risk:** Info. No action needed.

### O2. `GET /api/v1/whitelist` remains unauthenticated — Info

The 2nd audit noted this was "lower risk" (read-only exposure). N3 fixed the mutation path (`POST`), but the read path (`GET`) still exposes the full whitelist without auth. This is consistent with the audit's recommendation.

**Risk:** Info. Acceptable for current deployment.

### O3. Remaining `catch {}` blocks in non-audited files — Info

7 bare `catch {}` blocks remain in the codebase outside the audit scope (R1-R3):
- `sql-translator.ts:L82` — SQL parse fallback
- `http-server.ts:L717` — Whitelist JSON parse fallback
- `http-server.ts:L1271` — Session cookie parse (existing, pre-audit)
- `redis-server.ts:L623` — Redis protocol error handling
- `message-broker-adapter.ts:L185,L187,L231` — Pub/Sub callback error handling

These were not in scope for the R1-R3 audit items. Most are in protocol adapters where silent failure is the intended behavior (malformed input from external protocols). The `http-server.ts:L717` whitelist parse fallback is acceptable — it returns the default whitelist on malformed JSON.

**Risk:** Info. Protocol-level silent catches are acceptable. No action needed.
