## 1. Smart Contract — PlugPortAuth.sol (448 lines, NEW)

### Architecture ✅
- Self-sovereign: only `msg.sender` (direct) or verified EIP-712 signer (meta-tx) can manage their own keys.
- Gas station pattern correct: `onlyGasStation` modifier on `registerKeyMeta`/`revokeKeyMeta`.
- `DOMAIN_SEPARATOR` computed with `block.chainid` + `address(this)` at deploy time — correct for EIP-712.
- Nonce-based replay protection incremented before key operation — correct ordering.

### Findings

| ID | Severity | Finding | Location |
|----|----------|---------|----------|
| **S1** | 🟡 Medium | **`rotateKey` order-of-operations — old key is revoked AFTER new key is registered.** If `_registerKey` succeeds but `_revokeKey` fails (e.g., old key already revoked), the user ends up with an extra active key but no revocation. This is not exploitable (10-key cap protects abuse) but is a correctness issue. Consider revoking first, then registering, or wrapping both in a revert-on-failure pattern. | `PlugPortAuth.sol:169-171` |
| **S2** | 🟡 Medium | **No `rotateMeta` meta-transaction function.** `rotateKey` only has a direct version — users must hold MON to rotate. The gas station can register and revoke individually, but not atomically rotate. Dashboard would need to chain `revokeKeyMeta` + `registerKeyMeta` as two separate transactions, losing atomicity. Consider adding `rotateKeyMeta`. | `PlugPortAuth.sol` (missing) |
| **S3** | 🟢 Low | **`DOMAIN_SEPARATOR` is `immutable` — not EIP-2612 compliant for chain forks.** If Monad forks, the `DOMAIN_SEPARATOR` won't update to the new `chainId`. For testnet this is irrelevant, but for mainnet consider computing it dynamically or caching with chain-ID check (OpenZeppelin's `EIP712` does this). | `PlugPortAuth.sol:80` |
| **S4** | 🟢 Low | **`getActiveKeys` unbounded loop could hit gas limit for view functions.** With `MAX_KEYS_PER_ADDRESS = 10`, the double loop is bounded at 20 iterations total — this is safe in practice. No action needed. | `PlugPortAuth.sol:335-354` |
| **S5** | 🟢 Info | **`_recoverSigner` correctly enforces EIP-2 `s` value restriction** and rejects `v != 27|28`. The `ecrecover` `address(0)` check is present. Signature handling is secure. | `PlugPortAuth.sol:430-449` |

## 2. SCRAM-SHA-256 — wire-server.ts

### Architecture ✅
- Full `saslStart`/`saslContinue` handshake implemented correctly.
- `timingSafeEqual` used for `recoveredStoredKey` vs `storedKey` comparison — constant-time.
- Server nonce appended to client nonce — correct per RFC 5802.
- `scramSessions` cleaned up on success, failure, and nonce mismatch — no resource leak.
- On-chain verifier lookup tried first for `0x`-prefixed usernames — correct fallback chain.

### Findings

| ID | Severity | Finding | Location |
|----|----------|---------|----------|
| **B1** | 🟡 Medium | **`scramSessions` is an unbounded `Map` — potential memory leak.** If a client sends `saslStart` but never sends `saslContinue`, the session object is never cleaned up. A malicious client could open thousands of connections, each sending `saslStart`, to exhaust server memory. Add a TTL-based cleanup (e.g., delete sessions older than 60s) or cap the map size. | `wire-server.ts:423-431` |
| **B2** | 🟢 Low | **On-chain verifier lookup always uses `keyIndex: 0`.** If a user registered multiple keys and is connecting with key #3, the server will always read verifiers for key #0. The `username` field in SCRAM is typically the wallet address — there's no mechanism to specify which key index to use. Consider allowing `username` format like `0xAddress:3` or defaulting to trying all active keys. | `wire-server.ts:397` |
| **B3** | 🟢 Low | **`salt` truncated to 16 bytes from 32-byte `bytes32`.** The on-chain `salt` is `keccak256(abi.encodePacked(owner, keyIndex))` which is 32 bytes, but `subarray(0, 16)` truncates it. The local fallback also uses 16 bytes. Consistent, but the dashboard must also truncate identically during key generation. Verify client-side matches. | `wire-server.ts:400` |

## 3. Aggregation Pipeline — wire-server.ts + http-server.ts

### Architecture ✅
- Pipeline executor iterates stages sequentially — correct semantics.
- `$lookup` uses a hash index for O(n+m) performance instead of O(n*m) nested loop — good.
- `getNestedField` helper supports dot notation (e.g., `user.address`) — correct.
- `$project` handles both inclusion and exclusion modes, preserves `_id` unless explicitly excluded.
- `$unwind` drops documents with null/missing/empty arrays — matches MongoDB behavior.
- HTTP endpoint `POST /aggregate` wired with proper error handling.

### Findings

| ID | Severity | Finding | Location |
|----|----------|---------|----------|
| **B4** | 🟡 Medium | **No pipeline size limit.** A client can send an arbitrarily long pipeline (1000 stages) causing excessive CPU. Consider capping pipeline length to a reasonable maximum (e.g., 50 stages). | `wire-server.ts:585` |
| **I1** | 🟢 Low | **Unsupported pipeline stages are silently skipped.** The `default` case in the stage switch does nothing. Consider logging a warning or returning an error for unknown stages (e.g., `$group`, `$addFields`) to prevent user confusion when they use an unsupported stage and get unexpected results. | `wire-server.ts:900-901` |
| **I2** | 🟢 Low | **`$lookup` reads ALL documents from foreign collection via `store.find()`.** For large foreign collections, this loads everything into memory. The hash index helps, but the initial load is unbounded. Consider applying the `DEFAULT_QUERY_LIMIT` to the foreign collection scan, or at minimum add a warning log when the foreign collection exceeds a threshold. | `wire-server.ts:843` |

## 4. CSRF Protection — http-server.ts + dashboard api.ts

### Architecture ✅
- Double-submit cookie pattern implemented correctly: token stored in encrypted `iron-session` AND non-httpOnly `plugport_csrf` cookie.
- Server validates `x-csrf-token` header against `session.csrfToken` for POST/PUT/DELETE.
- GET/HEAD/OPTIONS exempt — correct per CSRF defense best practices.
- API key auth and test backdoor correctly exempt — CSRF only applies to cookie-based session auth.
- Dashboard `apiPost`/`apiPut`/`apiDelete` all attach `x-csrf-token` from cookie.
- Auth endpoints (`/auth/*`) exempt in dashboard — correct since nonce/verify establish the session.
- CSRF cookie cleared on logout — correct.

### Findings

| ID | Severity | Finding | Location |
|----|----------|---------|----------|
| **S5** | 🟢 Low | **CSRF exemption for `/auth/*` in dashboard is URL-prefix based.** The check `!path.startsWith('/api/v1/auth/')` exempts ALL auth paths including the new `/auth/register-key` and `/auth/revoke-key` endpoints. Since these are called with session auth from the dashboard, they should be CSRF-protected. Update the exemption to only exclude `/auth/nonce`, `/auth/verify`, `/auth/me`, and `/auth/logout`. | `dashboard/src/lib/api.ts:106` |

## 6. Auth Contract Adapter — auth-contract.ts (298 lines, NEW)

### Architecture ✅
- Singleton pattern via `getAuthContract()` — avoids multiple ethers connections.
- Graceful fallback: `isConfigured` / `isReadable` checks prevent crashes when env vars are missing.
- Read operations use `readContract` (no signer, free `eth_call`).
- Write operations use `writeContract` with gas station wallet.
- `registerKeyMeta` correctly parses `KeyRegistered` event to return assigned `keyIndex`.
- All read methods wrap in `try/catch` and return safe defaults (empty arrays, `false`, `0`).

### Findings

| ID | Severity | Finding | Location |
|----|----------|---------|----------|
| **I3** | 🟢 Low | **`readContract` is initialized even when `contractAddress` is empty.** `new ethers.Contract('', ABI, provider)` will create a contract instance with an empty address, which will throw on any actual call. The `isReadable` check guards against this, but it's wasteful. Consider conditionally creating the contract only when the address is non-empty. | `auth-contract.ts:80` |
| **I4** | 🟢 Low | **`getActiveKeys` makes N+1 RPC calls** (1 for `getActiveKeys` + N for `getCommitment` + N for `getVerifier` per active key). With 10 keys, that's 21 RPC calls. Consider adding a single view function to the contract that returns all key details in one call, or use `ethers.Contract.multicall` if available. | `auth-contract.ts:165-185` |

## 7. Redis Commands — redis-server.ts

### Architecture ✅
- `HMSET` correctly merges into existing hash document (JSON parse → update fields → JSON stringify).
- `HMGET` returns `nil` for missing fields via `encodeBulkString(null)` — matches Redis behavior.
- `RENAME` iterates all prefixes to find the key type — handles cross-type rename correctly.

### Findings

| ID | Severity | Finding | Location |
|----|----------|---------|----------|
| **I5** | 🟢 Low | **`RENAME` doesn't check if `newName` already exists.** Redis `RENAME` spec says the destination key is overwritten if it exists. The current implementation correctly handles this (KV `put` overwrites). However, if the old key and new key are different types (e.g., old is `redis:str:`, new already exists as `redis:hash:`), the old-type key is moved but the existing new-type key remains — resulting in two entries with the same logical key name but different types. Consider deleting all prefix variants of `newName` before the rename. | `redis-server.ts:485-512` |
