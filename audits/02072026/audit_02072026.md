## 2. Residual Issues (Carried Over)

These were acknowledged in the 1st audit as deferred or partially addressed. They remain in the codebase.

### R1. Silent catch blocks in `monaddb-adapter.ts` — Low

Two `catch {}` blocks remain:

1. **L111**: `loadKeyIndex()` — Catches all errors from `contract.getKeys()` with comment "Contract may not be deployed yet; silently ignore". This is intentional for initial startup but could mask RPC failures during normal operation.

2. **L202**: `count()` — `catch { return 0; }` when `contract.keyCount()` fails. Returns `0` instead of propagating the RPC error.

**Risk:** Low in dev mode (in-memory KV is used instead), medium in production where these are actual RPC calls.

### R2. Silent fire-and-forget catch in `http-server.ts:L175` — Low

```typescript
analyticsRecorder.record(...).catch(() => {}); // Fire-and-forget
```

Analytics recording failures are silently dropped. While this is intentional (don't block API responses for analytics), it eliminates all observability into analytics write failures.

### R3. Silent catch in `routing-adapter.ts:L140` — Low

```typescript
await this.privateAdapter.clear();
} catch { /* ignore */ }
```

Errors during private adapter `clear()` are silently ignored. Comment explains the rationale (potential double-clear idempotency), but could mask real failures.

## 3. New Findings

### N1. `GET /api/v1/collections/:name/roles` has no auth check — Medium (Security)

`http-server.ts:L958-L963`

```typescript
app.get('/api/v1/collections/:name/roles', async (req) => {
    const privacy = await privacyManager.getCollectionPrivacy(req.params.name);
    return { accessRoles: privacy?.accessRoles || {}, ok: 1 };
});
```

**Problem:** Anyone can enumerate the access control list (wallet addresses and their roles) for any collection — including private ones. This leaks the set of addresses that have been granted access. A malicious actor can map out the ACL of every private collection without authentication.

**Fix:** At minimum, require authentication. Ideally, restrict to the collection owner only (consistent with `POST /roles`).

---

### N2. `GET /api/v1/collections/:name/privacy` leaks owner address — Low (Information Disclosure)

`http-server.ts:L931-L936`

```typescript
app.get('/api/v1/collections/:name/privacy', async (req) => {
    const privacy = await privacyManager.getCollectionPrivacy(req.params.name);
    return { privacy, ok: 1 };
});
```

**Problem:** Returns the full `CollectionPrivacy` object including `ownerAddress`, `mode`, `accessRoles`, `contractAddress`, and timestamps — all without authentication. While knowing the privacy mode is useful, exposing the owner address and contract address to unauthenticated users is an information leak.

**Note:** The integration tests depend on this being unauthenticated for the "get default privacy" test case. A fix would need to either make the test pass a test auth header or return a reduced payload for unauthenticated callers.

---

### N3. `POST /api/v1/whitelist` (global) has no auth check — Medium (Security)

`http-server.ts:L727-L745`

```typescript
app.post('/api/v1/whitelist', async (req, reply) => {
    // ... No auth check!
    addresses.push(body.address);
    await saveWhitelist(addresses);
});
```

**Problem:** Any user (authenticated or not) can add or remove addresses from the global whitelist. This is a privileged operation that should be restricted to administrators or the server owner.

**Note:** The `GET /api/v1/whitelist` is also unauthenticated, but read-only exposure is lower risk.

---

### N4. `POST /api/v1/collections/:name/roles` does not validate ownership at HTTP layer — Medium (Security)

`http-server.ts:L965-L986`

While the endpoint requires authentication (`req.user?.address` check on L969), the ownership validation is delegated to `privacyManager.grantAccess()` / `revokeAccess()` which throw on mismatch. However:

1. The error is caught generically, and the endpoint returns the raw error message which may leak internal state.
2. More critically: if the collection has **no privacy settings configured**, `grantAccess()` throws `"Collection has no privacy settings configured"` — but the endpoint doesn't handle this gracefully. The caller gets a 500 instead of a meaningful 404.

**Fix:** Add an explicit ownership check before calling `grantAccess()`/`revokeAccess()` and handle the "no privacy configured" case with a 404.

---

### N5. Integration test cleanup (`afterAll`) returns 403 — Low (Test Quality)

From the CI output:
```
POST /api/v1/collections/test_integration_XXX/drop → 403
```

The `afterAll` hook tries to drop the test collection, but after setting it to `private` mode in an earlier test, the `checkAccess()` guard blocks the drop because the test doesn't pass the owner's auth header. The collection is never actually cleaned up.

**Impact:** Not a bug in production code. The in-memory store is destroyed when the server process ends, so no real leak occurs. But it's a test correctness issue — the cleanup is silently failing.

---

### N6. `B7` fix still uses `Number()` for the final conversion — Info

`http-server.ts:L1144`

```typescript
const balanceEth = Number(balanceWei * 1000000n / (10n ** 18n)) / 1000000;
```

While this is vastly better than the original `Number(balanceWei) / 1e18`, the intermediate result `balanceWei * 1000000n / (10n ** 18n)` still goes through `Number()`. For balances above ~9 billion MON (9e27 wei), the intermediate value exceeds `2^53` and precision is lost again. Given this is a testnet/early mainnet deployment where such balances are unrealistic, this is acceptable.

For reference, `ethers.formatEther()` avoids this entirely by using pure string arithmetic.

## 4. Architecture Assessment

### What's Working Well

1. **Auth architecture is solid.** The triple-auth middleware (session cookie → wallet-linked API key → legacy static key) is clean and well-layered. The SIWE flow using `iron-session` is stateless and multi-replica safe.

2. **Privacy routing is correct.** The `RoutingAdapter` properly routes metadata to public, collection data based on privacy mode, and merges global scans. The TTL cache on `PrivacyManager` reduces KV IOPS significantly.

3. **Component decomposition is clean.** The dashboard monolith split from 2,203 → 253 lines is substantial and the component boundaries are sensible.

4. **Test coverage is comprehensive.** 200 unit tests + 23 integration tests covering access control, routing logic, KV operations, and end-to-end API flows.

5. **Deploy configs are well-structured.** Separate Docker Compose overrides for testnet/mainnet, Kustomize overlays for K8s, and environment-specific `.env.*.example` files.

### Areas for Future Improvement

1. **Rate limiting on auth endpoints.** The global rate limiter (100 req/10s per IP) applies to auth endpoints, but `/auth/nonce` and `/auth/verify` should have stricter limits to prevent brute-force attacks.

2. **CSRF protection.** The CORS config with `credentials: true` + `SameSite` cookies provides baseline protection, but no explicit CSRF tokens are used. For the current cookie-based SIWE flow this is acceptable since the nonce serves a similar purpose, but should be revisited if non-SIWE mutations are added.
